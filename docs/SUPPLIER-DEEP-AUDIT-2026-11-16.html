Supplier Area — Deep Permission & Menu Audit

Full sweep: 82 route files, 150 views, 454 POST handlers, the 9-function permission core, and all ~90 menu items. Every finding cites file:line — open the file and check it. Dated 2026-11-16. 5 independent auditors; the HIGH findings re-verified by hand.

Bottom line (honest)

The permission engine is sound — fail-closed, IDOR-safe, no cross-tenant (cross-owner) leak, no self-escalation, CSRF everywhere. The problem is inconsistent application: the codebase has two gate functions — supplier_can() (scope-blind when no stay id is passed) and supplier_can_orgwide() (denies property-restricted staff). Some org-wide screens were converted to _orgwide; their siblings were missed. The result: a property-restricted ("selected"-scope) staffer, and in a couple of cases ANY staffer, can reach whole-business data and screens the owner believes are locked down. No outsider gets in; the leak is between staff inside one owner's org.

What is SOLID (verified, so you know it's not all broken)

  • OK No cross-owner leak. supplier_can() checks stays.user_id === owner when a stay id is passed (functions.php:753-766); a staffer's owner is bound from the supplier_staff row, never client input (:587). One owner's staff can never touch another owner's data.
  • OK No self-escalation. Role/staff editing lives only in supplierRolesRoutes + supplierStaffRoutes, both owner-only SUPPLIER_AUTH(). Staff can't edit their own role or invite staff.
  • OK Role builder is allow-listed. _supplier_role_build_perms() (supplierRolesRoutes.php:49-65) iterates the catalogue, not the POST — a hand-crafted POST can't grant a module/action that isn't in supplier_role_modules().
  • OK CSRF everywhere. All 454 POST handlers verify CSRF (directly or via a shared _ctx helper). The "POST>CSRF count" suspicion was a false positive in all 10 flagged files.
  • OK Staff accept flow is takeover-safe; approval-limit gate is fail-closed; suspended owner disables their whole team.
  • OK Property-mode menu passes the stay id correctly on all 34 items; no cross-property drop. Group-render has no empty-header / hidden-item leak.

FINDINGS — ranked, every one with code evidence

HIGH-1 — Customer Book: whole-org customer PII readable by a property-restricted clerk

supplierContactsRoutes.php gates the READ paths on plain supplier_can($db,'reservations','view') (:30 list, :75 search, :209 detail), then fetches by org (contacts_list($db,$orgId) :49/:82, contacts_get($db,$orgId,$id) :211). Same file's WRITE paths DO use supplier_can_orgwide (:133, :192, :258) — so the reads are a clear miss, not a design choice.

Who/what: a front-desk clerk whose role is scope_type='selected', limited to Property A, holding only reservations:view, opens /supplier/customers and reads every customer's name/email/phone/tax_id/credit_limit across Properties B, C… Walking /supplier/customers/{id} is a direct IDOR. Verified by hand.

HIGH-2 — Guest book: whole-org guest PII + loyalty readable/writable by a property-restricted clerk

supplierGuestsRoutes.php:27/:81/:112 gate on plain reservations:view/edit; data is org-keyed (guests_stored_list($db,$c['org']) :42/:115). The sibling supplierGuestCrmExtRoutes.php was correctly converted to _orgwide (:32,:79) — Guests was missed. A selected-scope clerk reads/edits every guest's PII + loyalty balance across all properties. Verified by hand.

HIGH-3 — Extended Procurement console reachable by a property-restricted staffer (money-posting)

supplierProcurementExtRoutes.php has zero _orgwide calls — every gate is plain supplier_can($db,'procurement',…) (:56,:108,…) and _proc_ext_org (:22) resolves the org for any staffer. The BASE console (supplierProcurementRoutes.php:24) correctly uses _orgwide. A selected-scope procurement staffer reaches requisitions/POs/GRN/three-way-match/budgets for properties outside their scope — and these POST to the GL. Verified by hand.

HIGH-4 — Alerts page has NO permission gate at all (presented as owner-only)

supplierNotifyExtRoutes.php:45 runs only SUPPLIER_OR_STAFF_AUTH + _notify_ext_ctx (:24-40), and that resolver has no permission check. So ANY active staffer — even a zero-permission role — opens /supplier/alerts and reads the org notification inbox. The sidebar hides it behind $isOwner (sidebar.php:219), so "owner-only" is false. (The supplier_can('finance','edit') at :64 only toggles the config buttons.) Verified by hand.

HIGH-5 — Marketplace & Executive-BI portfolio data readable by a property-restricted staffer

supplierMarketplaceRoutes.php:12 → marketplace_performance($db,$owner) (all stays' earnings/commission/quota). supplierBiExtRoutes.php:36/:68/:100/:123 → bi_ext_property_pl($db,$c['org_id']) (GL-derived revenue/expense/net P&L for EVERY property). Both gate on plain reservations:view, org-keyed, unnarrowed. A selected-scope clerk sees whole-portfolio financials. Verified by hand.

MEDIUM-6 — More org-admin screens admit a selected-scope staffer who holds the module permission

Same bug class, but requires the staffer to hold the org-admin permission (narrower than HIGH-1..5 which only need the near-ubiquitous reservations:view): Stores (supplierStoresExtRoutes.php:27, procurement), Workflow task board (supplierWorkflowExtRoutes.php, org-keyed task_list($db,$orgId)), Platform-ops config/auth-events (supplierPlatformopsExtRoutes.php:60…, platformops), Notify rules/webhooks (supplierNotifyExtRoutes.php:132…, finance:edit). All should use _orgwide.

MEDIUM-7 — Access-control (RBAC) console admits a staffer; contradicts the documented owner-only intent

supplierRbacExtRoutes.php:42/:47/:89/:112/:194 use SUPPLIER_OR_STAFF_AUTH + supplier_can('staff','view'/'edit'). A staffer granted staff reaches departments, the staff audit log, and the approval-decide queue — while functions.php:10590-10594 explicitly says staff grants are "INERT" because staff-mgmt is owner-only. Its siblings Staff/Roles correctly use SUPPLIER_AUTH(); RBAC is the inconsistent one. (Bounded: no role-editing / staff-invite is reachable here; decide re-checks supplier_can_approve.)

MEDIUM-8 — 8 menu items say "owner-only" but the route admits a staffer (hidden-but-reachable by URL)

Sidebar hides these behind $isOwner, but typing the URL works for a permission-holding (sometimes any) staffer: Alerts (no perm — see HIGH-4), Access control (staff:view — MED-7), Executive BI & AI & automation (reservations:view), Smart locks, Smart building, Apartments (rooms:view), Lease billing (hotels:view). The owner's "this is locked to me" belief is false for all 8. Full list + file:line in the sidebar table.

LOW — menu mismatches that annoy but don't leak

  • Dead links for selected-scope staff (MISMATCH-A): Guest CRM, Guest journey, Loyalty — sidebar shows them (plain $can), route denies them (_orgwide). They click, get bounced.
  • Hidden features (MISMATCH-B): Maintenance, Engineering, Events, Night audit, POS, Edit-property — sidebar requires edit, route only needs view, so a view-delegated staffer never sees a link they're entitled to.
  • Wrong module: Vendors route gates on rooms not procurement (supplierVendorsExtRoutes.php:49) — a vendor ledger behind the rooms permission; POS route gates on rooms:view while the sidebar uses reservations:edit.
  • Dormant parallel catalogue (functions.php:10752, 'active'=>false) + inert staff grant — latent footguns, not live bugs.

The ONE fix pattern (already proven in this codebase)

Every HIGH/MEDIUM finding is the same swap: on an org-wide read/write, change supplier_can($db,$m,$a) → supplier_can_orgwide($db,$m,$a) — exactly what the finance files, supplierGuestCrmExtRoutes, and supplierCommsExtRoutes already do. For the 8 "owner-only" menu items, either demote the sidebar from $isOwner to the real permission, or raise the route to owner-only — pick per item based on whether you actually want to delegate it.

Priority order if you want these fixed

  1. HIGH-4 Alerts (no gate — worst) → add an orgwide gate.
  2. HIGH-1/2/3/5 (Contacts reads, Guests, Procurement-ext, Marketplace/BI) → _orgwide.
  3. MED-6/7 (Stores/Workflow/Platformops/Notify/RBAC) → _orgwide / owner-only.
  4. MED-8 + LOW menu reconciliation (sidebar ↔ route parity).

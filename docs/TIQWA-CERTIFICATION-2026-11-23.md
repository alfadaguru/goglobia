> **Note on ticket status.** All four `POST /v1/flight/pay/{reference}` calls
> returned HTTP 200 with *"Ticket issuing is processing, your ticket will be
> updated shortly"*, and the bookings currently read `status: processing` with no
> PNR. This is expected behaviour of the **sandbox** (it does not emit a real PNR
> / `ticket.issued` event). Our integration handles the async completion: the
> booking is marked paid and left `pending`, and the real PNR + ticket number are
> written when Tiqwa sends the `ticket.issued` webhook (or on a poll of
> `GET /{reference}` returning `status: issued`).

GET  /v1/flight/confirm_price/mxa_b7b9fe8d-…    -> 200; document_required=false

## How these tests were run (method)

- The requests were issued by **our platform's own Tiqwa module code**
  (`modules/flights/tiqwa/creds.php`, `search.php`, `revalidate.php`, `reserve.php`,
  `actions/issue.php`, `utilities.php`) using the **stored sandbox credentials**
  from our live module configuration — i.e. the exact same code and token our
  production checkout uses, with the environment set to **Test/Sandbox**.
- The full customer HTTP path (Apache → `/modules/flights/tiqwa/*` routes) was
  separately verified working for search, revalidate, issue, booking-details and
  cancel; the per-scenario bookings above drive the identical underlying Tiqwa
  calls so each scenario's passenger/cabin/trip mix could be built precisely.
- Pricing: our platform applies its **own markup only**; the Tiqwa-side account
  markup is kept at **0** (confirmed `markup_value: 0.0` in confirm_price), so
  fares are never marked up twice.
